# ADR-0008: Build against C++23, chosen by measurement

- Status: accepted
- Date: 2026-08-31
- Supersedes: the language-standard clause of ADR-0001. Everything else in ADR-0001 — the
  Pico SDK, PIO for the bus, `make` as the entry point — stands unchanged.

## Context

ADR-0001 specified C++17. That was a default, not a decision: the ADR argues C++ over
MicroPython and PIO over the SPI peripheral, and never argues `17` over anything. The
operator asked why, which is the right question to ask of an unjustified number.

The binding constraint is not taste. `src/core/` compiles with **both** the host compiler
(host tests, ADR-0002) and the ARM cross-compiler (firmware), so the usable standard is
the intersection of what those two implement — not what either one advertises.

Measuring required installing the ARM toolchain, which the phase plan did not schedule
until `03-pio-bus`. That was itself a defect: `01-ps2-codec` writes all of `core` and does
not depend on `03`, so the language standard would have been frozen by phase `01` with the
constraining compiler never having been run. The toolchain was installed early to close
that gap.

**A trap found while installing, recorded here because it costs an hour to rediscover:**
Homebrew has two arm-none-eabi toolchains and the wrong one wins on `PATH`. The formula
`arm-none-eabi-gcc` (16.2.0) installs without `sudo` and ships **no target C library** —
`#include <cstdint>` fails, so it cannot compile any standard-library code and cannot
build Pico SDK firmware. The cask `gcc-arm-embedded` (15.3.rel1, GCC 15.3.1) does bundle
newlib and libstdc++, and needs `sudo` in a real terminal. There is no
`arm-none-eabi-newlib` formula. Installing "the ARM compiler" via the obvious command
produces something that looks installed and cannot compile. R-TOOL-02 exists to catch it.

## Decision

C++23, for firmware and host tests alike.

Measured on `arm-none-eabi-g++ 15.3.1` targeting cortex-m0plus, `-Os -ffunction-sections
-fno-exceptions -fno-rtti`, against Apple clang 21 on the host:

| feature | needed for | arm-gcc 15.3.1 | clang 21 |
|---|---|---|---|
| designated initializers | `pins.h` fields named at point of use (R-SAFETY-01..03) | yes, C++20 | yes |
| `std::span` | `decode( span )` instead of pointer+length | yes, C++20 | yes |
| `std::expected` | ADR-0009 | yes, C++23 | yes, C++23 |
| `#embed` | possible use for `tests/vectors/` | yes, at C++23 | yes, at C++23 |
| `std::inplace_vector` | fixed-capacity buffer without the heap (R-ARCH-03) | **absent** | **absent** |
| contracts | `pre`/`post` on safety-critical paths | **absent** | **absent** |

Cost of the headline C++20 feature, same source, same flags:

```
C++17 positional pin table    .text = 65 bytes
C++20 designated pin table    .text = 65 bytes
C++23 designated pin table    .text = 65 bytes
```

Byte-identical. The legibility gain — which in `pins.h` is a safety gain, because a wrong
drive mode has to be visible — is free.

**C++26 was measured and rejected.** Both compilers accept `-std=c++26`, which proves
nothing; what they implement is what matters. The intersection adds `pack_indexing`
(template metaprogramming with no use in this project) and nothing else. `ranges_concat`
is GCC-only, and ranges are code-size poison on an M0+ regardless. Both candidate features
that would genuinely have helped — `std::inplace_vector` and contracts — are absent from
both. Against zero measured benefit stands a real cost: GCC documents `-std=c++26` as
experimental and incomplete, and the two compilers' C++26 subsets already visibly differ.
Building `core` on the intersection of two moving, incomplete subsets is the wrong
foundation for a project whose premise is deterministic verification.

## Consequences

Easier: the pin table names its fields at the point of use; buffer APIs take one `span`
instead of a pointer and a length that can disagree; `std::expected` becomes available,
which ADR-0009 spends.

Harder: the Pico SDK defaults to C++17, so `CMAKE_CXX_STANDARD` must be set explicitly in
phase `03` — a one-line override that will fail loudly if it is forgotten, not silently.
The floor on the ARM toolchain rises to a GCC that ships `<expected>`; R-TOOL-01 makes
that floor a check instead of a README sentence.

**What would reverse this decision**, stated so a future reader does not have to guess:
`std::inplace_vector` landing in both compilers. It is the one C++26 feature with a real
identified use here — a fixed-capacity buffer with no heap is exactly what R-ARCH-03 wants
when it bans `std::vector`. If it appears in both, C++26 is worth re-measuring, and that
re-measurement gets its own ADR superseding this one.

Rejected:
- **Staying on C++17** — costs the named pin table for nothing; the measurement shows the
  alternative is free.
- **C++20** — would have been defensible and stops one feature short of `std::expected`,
  which measurement shows costs nothing and removes code we would otherwise own (ADR-0009).
- **C++26** — see above; measured, not assumed.
- **Deciding before installing the ARM toolchain** — the compiler that constrains the
  answer would never have been run. This is the failure the early install removed.

## Verification

Only GCC 15.3.1 was measured. R-TOOL-01 sets the floor at GCC 12, the release in which
libstdc++ gained `<expected>`; **that floor is inferred from the library's history, not
tested here.** Anything between 12 and 15.3.1 is unverified, and a failure in that range
is a finding to record, not a surprise to debug from scratch.
