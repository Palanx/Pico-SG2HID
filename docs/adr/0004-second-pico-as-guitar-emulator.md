# ADR-0004: Test against a second Pico emulating the guitar, not against the guitar

- Status: accepted
- Date: 2026-08-31

## Context

The operator has two Picos and a multimeter, and no logic analyzer. There is exactly
one SG and it is not replaceable. Two constraints follow: automated tests cannot depend
on the real guitar, and the real guitar must not be the thing that first exercises
untested bus code — a firmware bug that drives `DATA` while the controller drives it
is a short circuit between two output stages, and a wiring mistake found that way is
found on the irreplaceable device.

## Decision

The second Pico runs `src/emu/`, a binary that behaves as a PS2 controller on the bus:
it responds to `ATT`, shifts out a controller id and report bytes, pulls `ACK` low with
realistic timing, and can be told to answer as digital or as analog. It is the device
under test for every hardware-in-the-loop phase.

The order is fixed and is a safety property, not a preference:

1. Pure logic, host tests, no hardware (`01`).
2. Bus code exercised in loopback on one Pico (`03`).
3. Bus code exercised against the emulator, two Picos (`06`, `07`, `08`).
4. The real guitar, observed read-only through trace mode first (`09`).
5. The real guitar, full pipeline (`10`).

The real guitar is never a step in an automated test suite. Contact with it is always
an operator-driven, documented, manual procedure.

**The emulator shares `core` with the firmware, and that is a known hazard**: if both
sides derive their bytes from the same code, a bug in `core` is invisible because both
agree on it. The mitigation is that every expected byte sequence in the tests is a
literal, stored as hex in `tests/vectors/` and written from the protocol documentation
by hand — never generated by `core` and never captured from the emulator. Nothing under
`src/` may read that directory. This is a stated invariant with its own test, and it is
also why phase `09` exists: the real guitar is the only authority that can contradict
both sides at once.

## Consequences

Easier: the whole pipeline gets a deterministic, repeatable, automated test that costs
nothing to run and cannot damage anything; a regression is caught before the guitar is
ever plugged in; the emulator can be told to misbehave — drop an `ACK`, answer late,
report the wrong id — which is how the error paths get tested at all.

Harder: the emulator is a second protocol implementation to write and keep honest, and
it can be wrong in a way that makes a broken firmware look correct. The literal-vector
rule and phase `09` are the answer, and neither is free.

Rejected:
- **Testing against the guitar from the start** — every test is a physical setup, the
  error paths are untestable, and the first exercise of untested bus code lands on the
  irreplaceable device.
- **A pure software simulation of the bus in the host tests, with no second Pico** —
  kept and worth having, but it cannot catch a timing bug, which is the entire class of
  bug this project is about.
