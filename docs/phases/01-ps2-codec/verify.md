# Phase 01-ps2-codec — how to check this yourself

Written for someone who does not write C++ and has never read a controller protocol.
Nothing here needs the Pico, the guitar, a soldering iron, or any hardware at all. It runs
on the laptop in about two minutes.

## What was built

The **whole brain of the project, and none of its body.**

Everything this phase produced answers one question: *given these bytes, what is the guitar
doing?* Nothing in it can read a pin, drive a wire, or look at a clock. That is deliberate,
and it is what lets you run all of it on a laptop with the guitar still in its case.

Five pieces, all under `src/core/`:

| File | What it does |
|---|---|
| `ps2_protocol.h` | The vocabulary: which byte means "poll the controller", which means "ready", which controller ids we recognise. |
| `ps2_frame.h/.cpp` | The decoder. Takes raw bytes, returns either a frame or a reason there isn't one. |
| `guitar_state.h/.cpp` | Turns a frame into controls: five frets, two strum directions, start, select, tilt, whammy. |
| `link.h/.cpp` | Remembers what the controller currently is to us — absent, negotiating, or streaming — and why it last dropped. |
| `hid_report.h/.cpp` | Packs those controls into the exact bytes the USB side will send to macOS or Debian. |

## What a PS2 poll frame actually is

You need this to read the rest, and it is three ideas.

The Pico and the controller talk in **fixed-length exchanges**. The Pico says "wake up,
report yourself", and the controller answers with a short run of bytes. One such exchange is
a **frame**.

A frame the controller sends has three parts, in order:

```
   0x41      0x5A      0xFF  0xFF
   ^         ^         ^^^^^^^^^^
   header    "ready"   payload
```

1. **The header** says which kind of controller is answering — `0x41` means it is in simple
   digital mode, `0x73` means analog mode (the one where the whammy bar exists), `0xF3` means
   it is mid-configuration.

2. **The ready byte** is always `0x5A`. It is a sanity handshake: something that answers with
   anything else is talking, but it is not talking *this* protocol.

3. **The payload** is the actual button and axis data. Here is the clever part, and it is the
   single most important fact in this phase: **the header announces how long the payload
   is.** The bottom half of the header byte, times two, is the payload length. `0x41` ends in
   `1`, so two payload bytes. `0x73` ends in `3`, so six. The controller tells you how much
   it is about to say before it says it.

That last fact is what makes a whole class of bug detectable. If the header promised six
bytes and only four arrived, **something went wrong on the wire** — and we know it, because
we were told the number in advance.

### One more thing that trips everyone up

PS2 buttons are **active low**. A bit is `1` when the button is *released* and `0` when it is
*held*. So a frame where nothing is pressed reads `0xFF 0xFF` — all ones — and a guitar with
every fret held down reads closer to `0x00`. It is backwards from what anyone expects, it is
genuinely how the hardware works, and reading it the obvious way gives you a guitar that
reports every button pressed at all times.

USB HID is the opposite — there a `1` bit means pressed. The flip happens in
`guitar_state.cpp`, once, in a function called `is_pressed`, so that by the time anything
else touches the data it already means what it says.

## What the ten vectors are, and why they are written by hand

Under `tests/vectors/` there are ten small files. Each one is a frame, written out byte by
byte, with a comment on every single byte saying what it is:

```c
constexpr std::uint8_t kDigitalIdle[] = {
    0x41,  // header — digital controller; low nibble 1 announces 1*2 = 2 payload bytes
    0x5A,  // ready byte
    0xFF,  // buttons 0 — active low, so every bit set means every button released
    0xFF,  // buttons 1 — likewise
};
```

These were typed out by hand from the protocol documentation. They were **not** produced by
running our own code, and that is the point, not an inconvenience.

Here is why it matters. Later in this project there will be a second Pico pretending to be a
guitar, so the real one can stay in its case. That emulator will share this same `src/core/`
code. If the expected bytes in the tests were generated by `core`, and `core` misread the
protocol, then the emulator would produce the same wrong bytes, the tests would compare wrong
against wrong, and everything would pass — right up until the real guitar arrived and
disagreed with all of it. A hand-written literal is the only thing in the loop that did not
come from our own misunderstanding.

The ten:

| Vector | What it is | What must happen |
|---|---|---|
| `digital_idle` | Nothing pressed | Decodes; every control released |
| `digital_pressed` | Green fret + strum up | Exactly those two, nothing else |
| `digital_whammy_absent` | Digital, payload chosen to trap a careless whammy read | Whammy reports **at rest** |
| `analog_idle` | Analog, sticks centred | Decodes as analog; whammy at rest |
| `analog_whammy_full` | Analog, whammy pushed all the way | Whammy reports full deflection |
| `config_mode` | The controller mid-configuration | Recognised, but it is not a button report |
| `not_ready` | A controller that answered, then stopped driving the data line | **Refused.** No frame. |
| `unknown_id` | A real controller id we do not support | **Refused.** No frame. |
| `truncated_ack` | A frame the wire cut short | **Refused.** No frame. |
| `truncated_not_ready` | Cut short *and* the data line gone idle — both faults at once | **Refused**, and refused as the *cut-short* one. No frame. |

The last four are the ones that matter most, and the next section is about why.

`not_ready` is worth a sentence on its own, because it is the one whose bytes look most
normal. The second byte of every answer is always `0x5A` — the controller saying "ready,
here it comes". In that vector it is `0xFF` instead. `0xFF` is not a random wrong number: the
data wire is held high by a resistor and pulled down by the controller when it wants to send
a `0`, so when nothing is driving the wire at all, every bit reads as `1` and a byte reads as
`0xFF`. So this vector is a controller that answered its name and then went quiet, while our
end kept asking. The right-looking number of bytes arrives; they just are not data. A decoder
that only counted bytes would accept it.

## The one idea this phase is built around: refusing by default

A decoder has two ways to handle a frame it does not understand. It can guess — take what
arrived, fill in the rest, hand back something that looks like an answer. Or it can refuse.

This one refuses, always, and there is a specific reason. A guessed frame is
**indistinguishable from a real one** by the time it reaches the rest of the program. If a
frame got cut off halfway and we filled the missing half with zeros, the code downstream sees
a perfectly ordinary frame that says "the player is holding nothing". You would see the
guitar drop notes and have no way to tell that from the player missing them.

So there is no path through this code that produces a half-filled frame. Either you get a
complete frame or you get the reason you didn't, and the reason is a value you have to look
at before you can reach anything else.

Three rules in `docs/constraints.md` say exactly this, and as of this phase all three are
enforced by a program rather than by good intentions:

- **R-PROTO-02** — a frame the wire cut short yields no frame, and the link drops to "absent".
- **R-PROTO-03** — a controller id we do not recognise is refused, never guessed at.
- **R-PROTO-04** — the whammy is read **only** from a frame that said it was in analog mode.

## What this phase does NOT prove

Read this part twice, because it is the one thing that could mislead you later.

**Nothing here has been checked against your actual guitar.** Not one byte position.

Which bit is the green fret, which of the four analog axes carries the whammy, what value the
whammy sits at when you are not touching it, whether your SG even reports the controller id
we expect — all of that is read off the protocol documentation and how these controllers are
commonly described. It is an educated guess. Every one of those spots in the code is marked
`TODO(09-guitar-observe)`, and phase `09-guitar-observe` exists for exactly one purpose: to
plug in the real guitar, watch what it actually says, and correct whatever is wrong.

So when the tests below pass, what they prove is: **the code does what the code says it
does.** They do not prove the guitar agrees. Those are different claims and this phase only
makes the first one.

You can see the marks yourself:

```
grep -rn 'TODO(09-guitar-observe)' src/core/
```

Expect three of them. If that prints nothing, someone has quietly deleted the honesty.

# Check it yourself — about 5 minutes, no hardware

## 1. Everything passes

```
make test
```

Expect it to end with `OK`, and to take roughly two minutes — runs on this machine have
landed between 1:40 and 2:20, and the phase's own limit is three. A run inside that spread is
normal, not a warning. Most of that time is the machinery from the last phase mutating its own
checks to prove they still work.

```
make lint
```

Expect two lines, both starting `ok:`, and nothing else. This is the one that checks naming
and formatting and magic numbers.

**If `make lint` fails but `make test` passed**, that is expected and not a contradiction:
`make test` skips the style tools when they are not installed, and `make lint` refuses to.
`make lint` is the authority.

## 2. Look at the codec's own output

```
python3 tests/test_ps2_codec.py
```

Expect one line per case and per rule, every one beginning `ok:`, and the last one reading
`rejection cases: 3/3`.

Read a few of them. They are written to be read — each says which vector it used and what it
claimed about it. The three lines naming `R-PROTO-02`, `R-PROTO-03` and `R-PROTO-04` are the
three rules above, restated as something that runs.

## 3. Break the refusal on purpose, by hand

This is the important one, and it is the whole reason to trust the rest. You are going to
make the decoder stop refusing a bad frame, and watch the tests notice.

The last phase established that a test which has never been seen to *fail* proves nothing —
a check that always says "ok" looks identical to one that works. The driver above automates
three such mutations. Do one yourself, once, so you have seen it rather than been told it.

**Work on a copy.** Do not do this in your real tree:

```
rm -rf /tmp/codec-check
cp -a ~/Git/pico-sg2hid /tmp/codec-check
cd /tmp/codec-check
```

(`cp -a`, not `git clone`. A clone copies only what has been committed, and this phase's work
may still be sitting uncommitted in your tree — you would end up mutating a file that isn't
there and seeing nothing happen.)

Open `src/core/ps2_protocol.h` and find this, near the bottom:

```c
    default:
        return std::nullopt;
```

That `std::nullopt` is the refusal. It means "that header byte is not a controller id I
know, and I am not going to pretend otherwise". Change that one line to:

```c
    default:
        return ControllerId::Digital;
```

You have just told the decoder: *whatever byte arrives, call it a digital controller.* Now
run the codec tests:

```
python3 tests/test_ps2_codec.py
```

**Expect it to fail.** Six lines turn to `FAIL`, and they are worth reading in order,
because each says a different thing:

```
  FAIL: unknown_id: refused as UnknownId, and no frame
  FAIL: link: an unknown id drops the link and records why
  FAIL: R-PROTO-03 (an unknown controller id is refused, a known one is not)
  FAIL: the codec cases do not pass against the real src/core/ (rc=1)
  FAIL: R-PROTO-03 rejection case: the anchor 'return std::nullopt;' is gone from
        src/core/ps2_protocol.h, so nothing was mutated
  FAIL: rejection cases: 2/3
```

The third line is the guarantee: **the rule is named**, so you do not have to work out which
of the project's rules you just broke — the failure tells you.

The fifth line is worth understanding too, because it looks like a complaint about your edit
and it is not a mistake. The driver normally makes this exact change itself, in a temporary
copy, to prove the rule can fail. You have already made it, so when the driver goes looking
for the original line to change, it is gone — and rather than silently changing nothing and
reporting success, it says so. A test that quietly mutates nothing and then passes is the
specific failure this project has been bitten by before.

The command exits non-zero. Check it if you like: `echo $?` right after, expect `1`. The rule in
`docs/constraints.md` is not a sentence anyone has to remember — break it and the build stops
and tells you which rule you broke.

Now throw the copy away:

```
cd ~/Git/pico-sg2hid && rm -rf /tmp/codec-check
```

## 4. Confirm the hand-written vectors are still hand-written

```
grep -rn 'tests/vectors' src/
```

Expect **no output at all**. Not one file under `src/` is allowed to know the vectors exist —
that is rule R-PROTO-05, and it is what keeps the test data independent of the code it tests.

```
ls tests/vectors/*.h | wc -l
```

Expect `10`.

## 5. Confirm every rule this phase owed has been settled

```
grep -c 'planned: 01-ps2-codec' docs/constraints.md
```

Expect `0`.

`planned:` is how this project tracks a rule that is written down but not yet enforced —
honest debt with an owner. This phase started owing seven of them. Six are now enforced by a
running program; one (`R-PROTO-01`, about the order the bits go out on the wire) was handed
to phase `03-pio-bus`, because it is a property of the wire and no laptop test can see it. A
seventh clause was split off as a new rule `R-PROTO-06` and handed to the same phase, for the
same reason.

```
grep -c 'planned: 03-pio-bus' docs/constraints.md
```

Expect `4` — the two that phase already owed, plus those two.

## 6. Two things that were measured, and disagreed with what was written down

Both are recorded in `docs/constraints.md` under **§Observed conventions**, with the date.
You do not need to do anything about them; they are here so the numbers in this repo mean
something.

**The style checker needed two flags nobody knew about.** `clang-tidy` was being run in a way
that could not compile the files it was checking, and — this is the nasty part — it reported
that as a *naming* violation, because it turns every error into the same kind of failure. So
a completely broken invocation looked exactly like badly named code. Two flags fix it, and
the notes record what the two earlier attempts at this each got wrong.

**The magic-number check has a blind spot, and it is declared rather than hidden.** The
checker that enforces "no unexplained numbers in the code" does not look inside a
`const something = ...` line — and that happens to be the most common way this codebase
writes things. It still catches numbers in arithmetic, comparisons, array indexing and
function arguments. The gap is written down in `docs/constraints.md` rather than left for
someone to discover the hard way.

## What "done" means here

When all six sections above behave as described, what you know is:

- The decoder refuses every malformed frame in the test set, and **you have watched it stop
  refusing and seen the build catch that.**
- The whammy cannot be read out of a frame that never reported analog mode.
- Every rule this phase owed is either enforced by a running program or explicitly handed to
  a later phase, with the reason recorded.
- **None of it has met the real guitar yet**, and every guessed byte position is marked with
  the phase that will confront it.

The next thing that touches hardware is `02-wiring`, which is where the multimeter comes out.
